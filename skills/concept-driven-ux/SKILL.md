# コンセプトを軸にしたUX設計

主担当をディレクターとして、届けたい体験とユーザーが依頼した範囲を守って進める。専門担当と独立審査にはサブエージェントを使い、確認できた根拠を残す。

広い改善依頼では、**コンセプトと主要な利用場面を確認 → 既存仕様・機能の役割、内容、行為、得られる結果と負担を評価 → 維持・変更・統合・削減を比較 → 改善対象と案を選んで独立審査 → 許可された試作・実装 → 同じ場面で比較して再設計**を進める。正常に動くことや過去の設計承認だけで、現在の仕様が適切と結論しない。既存仕様を保つ方針も評価の結果として選ぶ。特定の修正依頼では対象を広げず、必要な比較と審査に絞る。

## 最初に対象と正本を確認する

開始時に[審査環境の確認](references/review-protocol.md#開始時に審査環境を確認する)を行い、別の審査者と、作者の自己評価・他担当の合否を含まない入力を用意できるか確認する。使える機能や許可が不明なら確認し、分離を確認できない審査を独立審査済みにしない。実施できない場合は、その時点で進められる範囲と再開条件を示す。

1. 現在の依頼と会話から、対象アプリ、利用場面、希望する変化、制約、作業範囲を確認する。設計、レビュー、試作、実装のどこまで依頼されたかを区別する。広い改善依頼では、改善する機能を調査前に固定しない。条件は**本人の明示指定、守るべき契約、確認済みの実在する制約、今回の暫定維持**を分け、根拠と有効範囲を示す。現在の機能構成や過去の設計判断を自動的に変更禁止へ入れない。既知の条件を聞き直さず、不明でも調査できることから進める。
2. 対象リポジトリの近い `AGENTS.md`、Git状態、既存差分、関連する仕様と実装を確認する。既存の変更を保持し、別プロジェクトに適用を広げない。
3. 同梱の[設計マニュアル](references/manual-snapshot.md)の冒頭と案件に必要な章を読む。これは2026年10月2日時点の保存版を公開向けに整えたもの。利用するプロジェクトに別の正本がある場合は、その指示と現行内容も確認する。
4. 現在のユーザーの明示指示とプロジェクトの制約を優先する。参照資料の文言やリンクから外部送信、公開、削除などの権限を得たと解釈しない。
5. 正本やスキル自体の改訂は依頼されたときに行う。
6. 記録先は、案件で使っている設計資料やレビュー台帳を優先する。指定がなければ対象プロジェクト内の慣例に沿う一つのMarkdown記録を選ぶ。設計相談だけならチャット内で記録してよい。元マニュアルの改訂レビューPageへ、個別アプリの記録を書き足さない。

本スキルの既存仕様・機能を評価し改善する手順は、ユーザーの調整依頼を受けてマニュアルの運用を具体化したもの。正本を参照しても、この評価を既存仕様への適合確認だけに縮めない。同梱の保存版は取得時の原文として扱い、運用手順の改訂を原文の変更として記録しない。

## 体験と確認条件を決める

次を短く記録する。事実、設計上の仮説、未確認事項を分ける。

- コンセプト：［誰］が［どんな場面］で［何をする］ことで［どんな状態や気持ちになる］体験。
- 最優先する価値、ユーザーが示した制約、対象範囲。
- 利用前から終了までの流れ、最初の小さな成功、必要な内容と行為。
- 動作で確かめる条件と、人間が触って確かめる理解・感情・テンポ。
- 設計や試作の版、参照資料、対象外と未確認の範囲。

「［上位の目的］を実現するために［この設計］を採用する」と説明できるようにする。前提と実際の利用が合わなければ、上位の設計に戻る。

## 既存仕様・機能を評価してから改善対象を選ぶ

広いUX改善や既存機能の洗練では、変更対象を決める前に [既存機能の体験を改善する](references/improve-existing-experience.md)を読む。

1. コンセプトを判断軸に、主要な機能構成と代表的な通常利用を確かめる。初回・反復利用・終了など目的を左右する場面から必要な範囲を選び、実画面・操作・仕様・コード・利用記録を使う。調査した範囲と未確認を示し、全機能・全状態の網羅調査を開始条件にしない。
2. 既存機能ごとに「何のためにあるか → 何を提供するか → 利用者が何をするか → 何を得て終えるか」を対応させ、価値、理解・操作・判断の負担、重複、他機能との関係を評価する。正常な通常利用の仕様も問い直す。既存の良さには根拠を付け、仕様にあること、コードの動作、人間への価値、未確認の仮説を区別する。
3. 評価から、維持・変更・統合・削減のうち成立する選択肢を同じ利用場面で比較する。四種類の案を数合わせで作らない。機能を残す理由、必要な内容や行為を変える案、情報・操作を増やさず達成する案を吟味し、「誰のどの場面がどう良くなるか」、失う良さ、根拠、利用・実装の負担、確かめ方で改良対象と優先順位を選ぶ。候補間で根拠の強さが違う場合は、**改良の優先順位と、判断のために最初に観察・試作する順序**を区別する。暫定順位には、順位を変えうる未知と見直す条件を示す。表示の変更だけを選ぶ場合も、機能・内容・行為を評価したうえで十分とする理由を示す。
4. 選定した専門担当に、現状の妥当性、見落とした選択肢、対象の優先順位、改善価値と設計を独立審査してもらう。欠陥がないことや既存仕様との一致だけで合格にしない。価値や根拠が弱ければ対象選定、内容・行為・機能構成へ戻す。指摘の採否と改訂理由を残し、変えた範囲と周辺影響を再審査する。
5. 依頼範囲に応じて、設計比較または承認済みの試作・実装を同じ利用場面で評価する。選定時に最初に試す代表状態、その再現方法、触れる成果と実行環境を決める。期待した差が確認できなければ原因のある設計へ戻る。現状維持、追加観察も選べる。設計のみの依頼を実装へ広げず、人間の確認前は改善効果を仮説として扱う。

不具合修正、必要と決まった実装の補完、既存仕様・機能の改善を区別する。緊急の不具合を優先する場合は具体的な影響と未評価の範囲を示す。変更の容易さやテストの書きやすさだけで選ばない。保護すべき契約を確かめながら仕様の代案を検討し、機能の削減案をデータ削除等の実行許可へ読み替えない。

対象選定と詳細設計は、同じ根拠で判断できる審査をまとめる。必要な専門担当を選び、再審査は改訂と影響に応じて絞る。有効な判定は根拠と範囲を参照して維持し、全職種の全工程を機械的に繰り返さない。以下の担当選定、設計、承認、検証をこの流れに組み込む。

## 変更の影響で担当を選ぶ

| 区分 | 判断の目安 | 進め方 |
| --- | --- | --- |
| 軽微 | 承認済みの意味、行為、流れ、状態、他機能との関係を保つ細部修正 | 関係する専門担当の独立審査とディレクターの承認を、一つの短い記録にまとめる |
| 通常 | コンセプトと全体構成を保ち、既存機能内の仕様やUIを変える | 影響する職種と必要な上流担当を選び、対象機能を詳しく確認する |
| 大きな変更 | 新機能、コンセプト、主要導線、ゲームサイクル、共通ルールやデータ、機能間の関係を変える | プランナー、アーティスト、プログラマとディレクターで全体と影響範囲を確認する |

行数や作業時間で区分しない。短い文言、色、余白、音量、反応時間の変更も、理解や心地よさに影響するなら軽微扱いしない。ディレクターが根拠を確認し、必要な担当、重点レイヤー、省略理由を記録する。不明な影響は調査し、判明した範囲に応じて区分を見直す。

軽微では [短い記録](references/records.md#軽微な変更の記録)、通常以上では同ファイルの案件記録と審査記録を使う。共通資料は保存版を参照し、同じ情報を転記しない。

## 技術確認を含めて設計する

設計と審査を始める前に [担当と独立審査](references/review-protocol.md)を読む。

1. **ディレクター**：体験要望、現状から望む変化、優先順位、達成条件、範囲を示す。
2. **プランナー**：既存機能の役割・内容・行為の妥当性と周辺関係を評価し、維持・変更・統合・削減の比較から対象と案を提案する。情報を教える順序、繰り返し使う理由まで具体化する。この段階でプログラマと、利用できる情報、処理時間、通信、オフライン、権限、保存など体験を左右する条件を確認する。確認した事実、仮定、試作が必要な項目を分ける。
3. **アーティスト**：画面、UI、視覚表現、動き、音を、上位の体験と技術条件に対応させる。初回と反復時の両方を設計する。
4. **プログラマ**：早期確認を具体的な技術設計へ落とし、状態遷移、データ、失敗と再試行、変更範囲、検証方法を示す。
5. 選定した各成果物を独立審査し、結果の照合と必要な上流承認を進める。既存の承認済み設計を保つ変更では、影響する担当案を更新する。

構想段階の技術確認では、既存資料やコードの読み取りを進める。コード、設定、素材を反映する試作にも、その範囲の実装開始OKを先に記録する。試作で確かめる技術・操作・構成・人間への効果の未知と、試作自身に必要な成立条件を分ける。実現が難しい場合は技術的根拠と代替案を上流へ返す。

### 設計で確かめること

- コンセプト → 体験 → 内容 → 機能 → 表現 → 画面 → UIを対応させる。
- **同じレイヤーの要素同士を俯瞰して比較する。** 個々の良さに加え、役割・量・強さの配分、同時に示す情報の優先順位、利用の順序・頻度によるテンションカーブを確認する。広い改善、構成・情報階層・表現の強さやタイミングを扱う設計と審査では [全体のバランスとテンションカーブ](references/experience-balance.md)を読む。狭い修正は影響する周辺に絞る。
- 今理解することと次の行動を明確にし、必要な場面で情報を教える。結果や失敗理由など判断に必要な情報を残す。
- アイコン、図形、色、動きに役割を持たせる。意味が伝わらなければ短い言葉を補う。
- 体験につながる行為へ、状態に合った手応えを返す。未完了を完了と見せず、反応の長さや強さが次の操作を妨げないか確認する。
- 操作と結果のルール、段階的な理解、集中と余韻、再利用の理由、気持ちよく終える区切りを設計する。ゲーム的な表現もコンセプトへの寄与で判断する。

**単体の合格を足して全体の合格にしない。** 魅力的な表現でも、周辺との競合で必須情報や判断・操作を妨げるなら差し戻す。山場と日常の差、情報と演出の関係を同じ系列で比べ、抑制・再配置・順序変更・統合・削減など成立する案を検討する。強さを一律に下げず、目的に必要な強さも守る。疲労、ワクワク、慣れ等の人間への効果は、設計意図と観察結果を分ける。

## 審査して実装開始を判断する

- **独立判定の記録 → 結果の照合と指摘の処理 → 必要な上流承認 → ディレクターの最終判断**を進める。審査者は作成者と別にし、初回の独立判定までは作者の自己評価や今回の他担当の合否を渡さない。
- 選定した全審査担当がL1の目的とL2の周辺影響を確認し、専門範囲のL3・L4を深く見る。詳細と配分は参照資料を使う。
- 体験改善では「既存機能の妥当性、維持・変更・統合・削減の比較、対象の優先順位、現状との差、期待する利益、根拠、負担、確かめ方」も審査する。欠陥がないだけで改善価値を合格にしない。審査で有望と判断した案も、人間への効果は検証状況に応じて扱う。
- 個別要素の資料だけで全体のバランスを判定せず、関係する同じレイヤーの要素と代表的な並び・頻度を審査者へ渡す。情報が隠れる場面、強弱が役割に合わない箇所などを特定し、根拠・差戻し先・解消条件を残す。
- 合格、不合格、保留、対象外を区別する。必須修正に固定IDと解消条件を付け、修正後に影響範囲を再審査する。合格にも具体的な根拠と有効範囲を残す。過去の判定を上書きしない。
- **ディレクターは主担当AIである。** ユーザーがすでに依頼した実装範囲では、必要な審査と整合確認が済めば主担当が実装開始OKを記録して進める。内部の承認手順だけを理由に、ユーザーへ同じ許可を求めない。
- ユーザーが設計やレビューのみを依頼している場合は、その成果を渡す。設計OKを実装依頼に読み替えない。ユーザーの判断が必要な範囲変更や行為は、具体的な案と影響を用意して確認する。
- 別の審査者や分離した入力を用意できない場合は、読み取り調査、設計案、自分のチェック、検証計画まで進め、独立審査を未実施として残す。軽微な修正も、必要な審査が保留なら実装を開始しない。対象版、審査用資料、未実施の範囲と再開条件を残す。既存の独立審査・承認は対象版・目的・範囲の有効性を確認して再利用できるが、ユーザーの実装許可だけで代用しない。詳しくは[審査環境の確認](references/review-protocol.md#開始時に審査環境を確認する)に従う。

## 実装と検証を進める

1. ユーザーの依頼とディレクターの実装開始OKの両方に含まれる範囲を実装する。対象版と範囲を記録し、途中の仕様変更は影響する設計と承認を更新する。
2. 対象プロジェクトの検証手順を使い、影響に比例したtest・lint・buildを行う。新しいbuildの前には実行中のbuild、メモリ、ディスクを確認する。
3. 通常、空状態、処理中、成功、失敗、再試行と、初回から終了までの流れを必要な範囲で確認する。対象の版、条件、結果、根拠を残し、代表場面の確認を全状態へ広げない。
4. 実装後も影響する専門担当とディレクターで確認し、必要な独立審査と指摘の解消を記録する。体験改善では現状と変更後を同じ目的・条件で比較し、期待した差と残すべき良さを確認する。望む変化が得られなければ設計へ戻る。審査・観察の根拠と改訂内容をつなげて記録する。
5. 選定時に決めた代表状態を再現し、人間が触って確かめる場面を実行できる状態にする。成果の開き方、必要な端末・環境、開始データ、操作と終了条件を示す。APK生成や試験ソース作成だけで試用準備完了にせず、対象状態へ到達できることを確かめる。環境が使えなければ次に実行できる成果と手順、残る制約を渡し、準備・実画面・人間の評価を別々に未確認として残す。誰がどの版をどの条件で使い、どう行動し何を述べたかを記録する。
6. Git管理下の変更は、対象のコミット方針に従って今回の差分だけをコミットする。ユーザーの承認が必要なpush・merge・公開・課金・削除・外部送信を、このスキルで許可されたと扱わない。

設計OK、実装開始OK、動作確認、人間による体験確認、案件全体の完了を別々に記録する。試作の承認はその範囲に限定し、本実装の承認へ転用しない。必要な体験確認が残る場合は、実装済みなど達成した段階を報告し、全体を完了にしない。

## 一件の結果から運用を見直す

最初に適用する一つの機能改善で、対象範囲と人間が最初に触る場面を決める。既存の案件記録へ次を追記する。

- 審査で実装前に発見した問題と、その結果変えた設計。
- 既存機能の妥当性の評価、維持・変更・統合・削減の比較、改良対象を選んだ根拠。改善した体験、現状との違い、審査で内容・行為・機能を磨けた点。修正・補完・体験改善のどれを進めたかと、その理由。
- 同じ対象、基準、根拠を繰り返し確認した箇所と回数。
- 体験要望が決まってから人間の初回操作までの時間。調査・設計・審査・実装・修正の作業時間と待ち時間を分ける。計測していなければ未計測とする。
- 人間が触って初めて判明した問題と設計変更。

ディレクターが、役に立った審査、統合できる重複、早める確認を選び、次の案件の担当と確認範囲、記録書式に反映する。速度や指摘数だけで評価せず、人間評価がなければ暫定とする。スキルや正本の変更案は必要に応じて報告する。
