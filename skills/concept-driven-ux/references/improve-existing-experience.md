# コンセプトから既存仕様・機能を精査し、改善対象を選ぶ

広いUX改善や既存機能の洗練では、**コンセプトと通常利用 → 既存機能の役割・内容・行為の評価 → 維持・変更・統合・削減の比較 → 改良対象の選定 → 比較できる設計・試作 → 再評価**を進める。正常に動く仕様や機能の価値も問い直す。表示の整合性や不具合の有無だけで、仕様・機能が適切だと結論しない。

特定の不具合修正、指定済みの小変更、設計・レビューだけの依頼では、その範囲を守る。関連する仕様や周辺機能は影響確認に必要な範囲で調べ、広い監査や実装へ拡張しない。

## 1. 評価範囲と制約を分ける

主担当が、届けたい体験を表すL1のコンセプトと、アプリ全体の流れ・機能の関係を表すL2を短く確認する。コンセプトが資料からしか分からない場合は、現在のユーザーの依頼と照合し、推定を明記する。現在の実装から都合のよいコンセプトを逆算しない。

広い依頼では、改良対象を先に一画面・一表示へ固定しない。代表的な通常利用を、きっかけから結果を得て終えるまで追い、そこで使う主要機能と関連機能を選ぶ。初回、再利用、失敗などは、価値や判断を変える場面を追加する。全機能・全状態の網羅は要求せず、何を評価し、何をまだ評価していないか、その理由を残す。見なかった機能を適切と判定しない。

調査前に境界を次のように分ける。

- **本人の明示指定**：現在も有効なユーザーの選択、変更禁止、対象範囲。会話や指示の根拠を参照し、過去のAIの選定を本人の指定にしない。
- **守るべき契約**：保存データ、同意、互換性、利用者へ約束した動作等。何を損なってはいけないかと根拠を示し、現在の画面構成や数値設定そのものと区別する。
- **確認済みの実在する制約**：プロジェクトの指示、技術・運用条件。確認した版と制限範囲を示し、未調査の難しさを制約にしない。
- **今回の暫定維持**：比較の基準や調査範囲のため、今回保つ現在の仕様。維持する理由、未確認の価値、再評価する条件を示す。変更禁止や最善と確認済みの仕様に格上げしない。
- **再評価する設計**：既存の情報、計算・比較規則、操作、機能分担、画面構成、初回案内、過去の設計判断。採用済みや承認済みという理由だけで固定しない。
- **今回調べない範囲**：依頼や効果に照らして後に回す領域。単なる調査上の対象外を、変更禁止や価値確認済みに読み替えない。

既存のコードや仕様は「現在どう動くか」、過去の承認は「何を意図したか・どの範囲を承認したか」の根拠であり、現在の価値を証明しない。たとえば待ち時間の秒数や利用時間の固定値は、本人の指定・約束のある動作・今回の比較条件のどれかを根拠から判断する。値だけで保護対象としない。制約の変更が必要な案も比較には含められるが、実行は現在の依頼と許可に従う。

## 2. 正常に成立する既存体験を評価する

実画面・操作・仕様・コード・利用記録から、選んだ場面でユーザーが得るものを確かめる。対象版と参照を残し、事実、設計上の仮説、未確認事項を区別する。画面や操作を確認できなければ資料上の評価と明記し、人間の迷い・安心感・利用頻度を推測で事実にしない。

関連する主要機能について、以下を一つの短い記録に対応させる。表や文章は案件に合う形を選び、同じ根拠を何度も転記しない。

| 評価するもの | 記録する内容と問い |
| --- | --- |
| 役割と上位目的 | 誰のどの場面で、L1の価値とL2の流れをどう支えるか。その役割が現在も必要か |
| 提供する内容 | 情報・選択肢・結果は何か。利用者の目的や次の判断に役立つか、意味・確かさが伴うか |
| 利用者の行為 | 何を探し、入力し、選び、解釈するか。その行為が結果に必要か、目的に見合う負担か |
| 結果と区切り | 行為の後に何を得て、どう使い、どこで終えられるか。得た結果と次の行為がつながるか |
| 負担と他機能との関係 | 理解・学習・操作・待ち時間の負担、重複や分断、頻度、失うと困る価値は何か |
| 根拠と暫定判断 | 確認できた挙動・観察、仮説、未知を分け、現在の妥当性と残すべき良さを示す |

「表示を分かりやすくする」前に、「その内容を提供する必要があるか」「その行為や判断を求める必要があるか」を確かめる。技術的に正しい情報でも用途が弱ければ見直し候補になる。逆に、情報や操作を減らすために、結果の意味・重要な判断材料・失敗理由を失わない。

機能ごとの評価を終えたら、関係する同じレイヤーの要素を並べ、役割・量・強さの配分と流れの妥当性を評価する。experience-balance スキル（全体のバランスとテンションカーブ）に沿い、同時の注意競合、利用順序、頻度、初回と反復を必要な範囲で比べる。局所の良さが全体の目的や山場の効果を損なう場合も改善候補にする。

調査だけでは価値を判断できない場合、結論を埋めるために資料審査を増やさず、どの画面・操作・人間の観察で判断できるかを決める。必要なら、許可された範囲の最小限の比較用試作を次の段階に選ぶ。

## 3. 維持・変更・統合・削減を比較してから対象を選ぶ

評価で得た「現状 → 望む変化 → 誰にどう役立つか」を候補にする。不具合の修正、決定済みの不足実装の補完、正常に成立する既存体験の改善を区別する。広い依頼では、既存体験を評価した根拠と、そこから候補を選んだ理由を残す。容易な修正や発見した欠陥だけから改良対象を決めない。

候補ごとに、意味のある選択肢を吟味する。

- **維持**：現在の価値が目的に合い、変更による利益の根拠が弱い。良さを残すことや追加観察を選ぶ。
- **変更**：役割は必要だが、提供内容、求める行為、ルール、順序、反応などを変える方が目的に近づく。
- **統合**：関連機能や内容の重複・分断を解消して、理解や行為をつなげる。別々に使う場面や必要な区別を損なわないか確かめる。
- **削減**：価値の薄い情報・操作・機能を外す、後へ回す、必要時だけ見せる。減らしても目的と重要な判断が成立するか確かめる。

四種類すべての案を作る必要はない。選択肢を機能名だけで分類せず、実際に異なる内容・行為・結果を同じ場面で比べる。追加も必要な体験を実現する場合の選択肢だが、追加自体を改善と扱わない。意味のない代案や色だけ変えた案で比較を埋めない。指定済みの小変更は、範囲に必要な現状との比較でよい。

| 候補・方針 | 同じ場面での内容・行為・結果 | コンセプトへの寄与と根拠 | 失う良さ・増減する負担・制約 | 未確認事項と確かめ方 |
| --- | --- | --- | --- | --- |
| 現状維持 | 現在の流れと結果 | 維持できる価値、弱い点 | 現在の負担と守れる良さ | 比較の基準と未知 |
| 意味のある代案 | 何を変え、まとめ、減らすか | 誰のどの場面がどう良くなる見込みか | 利用・学習・実装の負担と周辺への影響 | 観察する行動・結果、判断条件 |

複数の改善候補を、コンセプトへの寄与、ユーザーの利益と不利益、場面の重要性、根拠の強さ、実現・検証の負担で比較して対象を選ぶ。数値不明の利用頻度や効果量は仮説とし、点数の合計で不確実性を隠さない。緊急の不具合を優先する場合はその影響を理由にし、それで既存体験の妥当性まで確認したと扱わない。

選定対象、維持するもの、後に回すもの、採らない案の理由を短く残す。根拠が足りなければ暫定選定や追加観察にする。表示変更に落ち着くことも、役割・内容・行為を検討した結果ならよい。広い評価から対象を絞る順序を守り、調査の開始時から表示だけを保護する前提を置かない。

**改善対象の順位と、確かめる順序を分ける。** コードで確認した局所的な問題と、利用者への影響がまだ不明な中核体験を比べる場合、「根拠が多い」「先に直せる」だけで局所改善を最優先にしない。順位を逆転させうる未知、結論に必要な代表場面、最初の観察・試作で確かめることを示す。利用記録、同じ条件での比較、観察等のどの根拠で順位を更新するかを決める。実際の頻度や影響が分からないまま最善の改良対象と断定せず、依頼範囲で暫定選定または観察先行を選ぶ。全候補の実測を開始条件にしない。

例：読書メモで「次に読むとき、前に考えたことを取り出す」が目的なら、正常に動く必須分類も評価する。分類を維持する案、保存時の分類を任意にする案、分類を後の整理機能へ統合する案を、同じ「一つの気づきを残し、翌日に探す」場面で比べる。入力時の判断を減らす利益と、探す負担が増える不利益の両方を見る。分類の用途や観察の根拠が足りなければ、維持または比較用試作を選ぶ。この架空例は、任意化や統合を推奨する定型ではない。

機能や内容を減らす案の比較と、保存データの削除や無承認の外部操作の実行は別である。現在の依頼や継続的な許可の範囲で進め、比較したことを実行許可にしない。すでに得た有効な許可を、このスキルだけを理由に聞き直さない。

## 4. 対象選定と案の価値を独立審査する

作成者と別の担当が、現状評価、比較候補、同じ根拠から独立判定する。独立判定まで作者の自己評価や他担当の今回の合否を渡さない。L1の目的とL2の周辺関係を確かめ、影響する機能・詳細を深く見る。案の選定と詳細設計が同じ版・範囲・根拠で判断できるなら一度に審査する。職種数や工程数を固定して反復しない。

審査では、実現性や欠陥の有無に加え、次を問う。

- 既存仕様・機能の役割、提供内容、利用者の行為は、現在のコンセプトと場面に適切か。維持する判断にも根拠があるか。
- 改良対象は現状評価から選ばれているか。正常に成立する重要な体験や、機能間の関係を早く対象外にしていないか。
- 維持・変更・統合・削減のうち、価値や負担を変える有力な代案を見落としていないか。制約と暫定設計を混ぜていないか。
- 選んだ案は、現状や他候補より優先して試す理由があるか。情報や操作を増やして問題を移すだけになっていないか。
- 候補間の根拠の差を価値の差と混同していないか。暫定順位を覆す条件と、先に確かめるべき未知が具体的か。
- 同じレイヤーの要素間で、役割・強弱・情報の優先順位と時間の流れは目的に合うか。個別の魅力が、全体の理解・判断・山場の効果を損なっていないか。
- 改善を確かめる場面と成果、判断条件が具体的か。資料だけで判断できない仮説は何か。

各審査者は、妥当な点と根拠、最も大きな弱点・不確実性、必須修正や必要な確認、合否と有効範囲を返す。欠陥が見つからないことを改善価値の合格にしない。現状維持が妥当ならその根拠を示し、無理に変更や指摘を作らない。

主担当は指摘の採否と理由を記録し、必要に応じて対象選定、役割、内容、行為へ戻す。修正後の再審査は指摘と影響範囲に絞り、未変更の同じ根拠を全員で再判定しない。未知が人間の経験なら、資料審査で合格に置き換えず、触れる比較成果へ進むための条件を示す。

## 5. 早く比較できる成果を作り、同じ場面で磨く

対象選定の時点で、最初に比較する代表場面、確かめる仮説、比較できる最小成果を決める。設計・レビューのみなら、具体的な流れや画面案と確認計画を成果にする。試作・実装が依頼に含まれる場合は、必要な審査と主担当のその範囲の実装開始OKを記録して進める。現在の許可の範囲で主担当が判断し、内部審査を理由に同じ実装許可を求め直さない。

比較用の試作は、案の違いが表れる範囲に絞る。許可された実装自体で比較できるなら別の試作は不要である。試作で測る技術・操作・構成・人間への効果の未知は検証条件にできるが、試作自身に必要な安全・契約・範囲の根拠や、その試作に適用する既知の必須修正は先に解決する。independent-review スキルの審査手順の開始条件を使い、本採用の保留を理由に未知を測る試作まで止めない。設計だけの依頼からアプリのコード・設定・素材の反映へ進まない。

人間が触れる成果は、起動方法、対象版、代表状態を再現する手順またはデータ、開始条件、何を確かめるかまで用意する。APKやテストソースが存在するだけで、初回操作の準備が整ったと扱わない。結果が出る場面まで触れる状態にし、用意できない部分を明記する。

比較では、利用目的、開始時の情報やデータ、操作条件、期待する変化、残すべき良さをそろえる。「情報から次の行動を決められる」「以前必要だった入力を省ける」など目的に合う行動・結果を観察する。速さやタップ数は目的に関係するときに使い、唯一の尺度にしない。人間には答えを教える誘導を避け、行動を観察した後に理由や感想を聞く。

AIの画面・操作確認で分かる構成や挙動、test・lint・buildの動作検証、人間の理解・気持ち・好みを分ける。実画面未確認、人間未確認、改善前を再現できない場合の比較制約はそのまま残す。設計の合格やビルド成功を、体験の改善が確認された根拠にしない。

記録は「比較した版 → 観察・審査の根拠 → 変えた内容と理由 → 再確認結果」とつなぐ。望んだ差が出なければ、表現だけの修正に限定せず、原因のある役割・内容・行為・対象選定へ戻る。別案、維持、追加観察も選べる。不具合を解消しただけで体験比較を終えない。

## 6. 判断と未確認を分けて引き渡す

必須指摘が解消し、その段階の条件を満たしたら次へ進む。固定回数の再設計や無期限の磨き込みを要求しない。次の判断に人間の観察が必要で、まだ実施できない場合は、触れる成果と具体的な確認手順を渡し、判断を保留する。

最後に、評価した機能と場面、既存仕様の妥当性、維持・変更・統合・削減の比較と選定理由、残す良さ、審査・観察から変えた点、対象版と根拠、動作と人間の体験それぞれの確認状況を簡潔に示す。未評価の領域と未確認の改善効果を成功に含めない。

## 7. 設計で確かめること

- コンセプト → 体験 → 内容 → 機能 → 表現 → 画面 → UIを対応させる。
- **同じレイヤーの要素同士を俯瞰して比較する。** 個々の良さに加え、役割・量・強さの配分、同時に示す情報の優先順位、利用の順序・頻度によるテンションカーブを確認する。広い改善、構成・情報階層・表現の強さやタイミングを扱う設計と審査では experience-balance スキル（全体のバランスとテンションカーブ）を読む。狭い修正は影響する周辺に絞る。
- 今理解することと次の行動を明確にし、情報を教える順序を決めて、必要な場面で情報を教える。結果や失敗理由など判断に必要な情報を残す。
- アイコン、図形、色、動きに役割を持たせる。意味が伝わらなければ短い言葉を補う。
- アクセシビリティを細部の審査に含める。文字の読みやすさ（大きさ・コントラスト）、色だけに頼らない区別、キーボードや読み上げでの操作と順序が、承認済みの意図どおりか確認する。対象プラットフォームの標準的な基準に照らし、確認していない項目は未確認として残す。
- 体験につながる行為へ、状態に合った手応えを返す。未完了を完了と見せず、反応の長さや強さが次の操作を妨げないか確認する。
- 操作と結果のルール、段階的な理解、集中と余韻、再利用の理由、気持ちよく終える区切りを設計する。ゲーム的な表現もコンセプトへの寄与で判断する。

**単体の合格を足して全体の合格にしない。** 魅力的な表現でも、周辺との競合で必須情報や判断・操作を妨げるなら差し戻す。山場と日常の差、情報と演出の関係を同じ系列で比べ、抑制・再配置・順序変更・統合・削減など成立する案を検討する。強さを一律に下げず、目的に必要な強さも守る。疲労、ワクワク、慣れ等の人間への効果は、設計意図と観察結果を分ける。
