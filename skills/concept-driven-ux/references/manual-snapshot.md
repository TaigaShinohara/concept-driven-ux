## 保存した本文

このマニュアルは、アプリの企画、機能設計、画面設計、改善で判断に迷ったときに使う。最も優先するのは、ユーザーに届けたい体験である。機能、情報、見た目、操作、リアクションは、その体験を実現するために設計する。

ここでいう「コンセプト理論」は、届けたい体験を明確にし、その目的から具体的な設計へ落とし込む方針を指す。

**すべての設計判断を、「これは、届けたい体験にどうつながるのか」で確かめる。**

## 届けたい体験を定義する

まず、誰に、どんな場面で、どんな体験を届けたいのかを言葉にする。コンセプトは、ユーザーが使う前後で何が変わるのかまで具体的にする。

- **誰に届けるか**：どんな状況や困りごとを持つ人か。

- **いつ使うか**：どんなきっかけや場面でアプリを開くか。

- **何を体験してほしいか**：何ができ、どう感じられるようになるか。

- **何を最優先するか**：便利さ、安心感、楽しさ、達成感などのうち、このアプリで守る価値は何か。

- **何を見て確かめるか**：ユーザーのどんな行動や感想があれば、その体験が届いたと判断できるか。

コンセプトは、次の形で一文にする。

> ［誰］が、［どんな場面］で、［何をする］ことで、［どんな状態や気持ちになる］体験を届ける。

例として、メモアプリなら「思いついたことを忘れそうな人が、その場で迷わず一言を残し、覚えておかなければという負担を手放せる体験を届ける」と定義できる。

この場合、すぐに書き始められることと、確かに保存されたとわかることが優先される。初回から細かな分類や設定を求める設計は、この体験に必要かを見直す。

## コンセプトから具体的な設計へ落とし込む

設計は、上位の目的から順に具体化する。

**コンセプト → 届けたい体験 → 提供する内容 → 必要な機能 → 理解を助けるデザイン → 画面構成 → UI**

| 段階 | 決めること | 上位の目的との照合 |
| --- | --- | --- |
| コンセプト | 誰に何を届けるアプリか | この判断は、最優先の価値を守っているか |
| 体験 | 使う前から使った後まで、何が変わるか | コンセプトを実感できる流れか |
| 内容 | 何を見せ、何をしてもらうか | その内容は、体験を生むために必要か |
| 機能 | 内容を実現する仕組み | 機能を足すことで、体験が良くなるか |
| デザイン | 意味や状態を伝える表現 | ユーザーの理解や気持ちを助けているか |
| 画面 | 情報と行動の順序やまとまり | 目的達成まで自然に進めるか |
| UI | ボタン、入力、配置、操作後の反応 | 今することと、その結果がわかるか |

デザインは全体の伝え方、画面は情報や行動のまとまり、UIはその場で触れる具体的な操作として考える。

各段階で、直上の目的とコンセプトの両方を確認する。機能を追加したとき、画面を分けたとき、ボタンの位置や動きを変えたときにも照合する。

判断の理由は、次の形で短く残す。

> ［上位の目的］を実現するために、［この設計］を採用する。

理由が説明できない要素は、削る、後に回す、別の表現にする候補にする。実際に使ってみて前提が違うとわかった場合は、上位の設計に戻って見直す。

## 情報を絞って一つずつ教える

一つの場面で、ユーザーが今理解することと、次に行うことを明確にする。複数の目的、説明、選択肢を同時に提示して負担を増やさない。

情報を絞るときは、次の順で考える。

1. この場面で、ユーザーは何を達成したいか。

2. そのために、今必要な情報は何か。

3. 操作した後に伝えてもよい情報は何か。

4. 詳細を見たい人だけに見せられる情報は何か。

5. 体験に役立たず、取り除ける情報は何か。

最初から全機能を説明する代わりに、小さな操作をしてもらい、その結果から一つずつ理解できるようにする。説明は、必要になる場面に置く。

メモアプリなら、最初は「一言を書く → 保存されたとわかる」までを体験してもらう。分類や検索の説明は、必要になった場面で伝える。

情報を減らす目的は、理解しやすくすること。操作の意味、重要な結果、失敗した理由など、判断に必要な情報まで省かない。

## アイコンや図形や動きに役割を持たせる

アイコン、図形、色、アニメーションを使い、言葉だけに頼らずに意味を伝える。どの表現にも、説明できる意図を持たせる。

| 表現 | 担わせる役割の例 | 設計時の問い |
| --- | --- | --- |
| アイコン | 行為、対象、状態を見分ける | この意味が伝わるか。短いラベルは必要か |
| 図形や配置 | 情報の関係、まとまり、優先順位を示す | 何が一組で、何を見るべきかわかるか |
| 色 | 選択、状態、重要度の違いを示す | 色以外でも違いがわかるか |
| アニメーション | 操作と結果をつなぎ、変化や位置を示す | 何がどう変わったかを理解しやすくするか |

メモが保存された場面なら、入力した内容が一覧に収まる動きで、保存先と操作の結果を伝えられる。

「賑やかだから」「流行っているから」だけでは採用しない。表現を取り除いたときに理解や手応えがどう変わるかを考え、役割を確かめる。

言葉を減らして意味が伝わらなくなる場合は、短い言葉を補う。動きは必要な変化に絞り、繰り返し使う際の待ち時間や負担も確認する。

## 体験につながる行為に嬉しい反応を返す

届けたい体験に直接つながる行為には、ユーザーが「やってよかった」と感じられる反応を返す。

ここでいう「褒める」は、称賛の言葉に限らない。操作の手応え、気持ちのいい動き、音、振動、変化の見え方、達成後の余韻を含めた、嬉しく感じる体験である。

次の順で設計する。

1. **認めたい行為を決める**：どの行為が、届けたい体験に近づくのか。

2. **結果を伝える**：何が起き、どんな価値が得られたのかをわかるようにする。

3. **嬉しさを加える**：その行為とアプリの雰囲気に合う反応を返す。

4. **次の行動を妨げない**：反応の長さや強さを調整する。

メモアプリで認めたいのは、思いついたことを残せた行為である。保存がわかる短い動きと、書いた内容が落ち着いて収まる表示で、手放せた感覚を支えられる。

すべての操作に大きな演出を付ける必要はない。日常的な小さな行為には軽い反応を、意味のある節目には少し豊かな反応を用意する。安心感が中心の体験なら、静かな反応が合うこともある。

反応は実際の状態に合わせる。保存中、保存完了、失敗を区別し、達成していないことを達成したように見せない。

## ゲームデザインを使って体験の流れを作る

ゲームデザインやレベルデザインの考え方を、理解、行動、手応え、繰り返しの設計に取り入れる。得点やランキングの追加も、コンセプトに役立つ場合に検討する。

### ロジックを一貫させる

ロジックは、操作、結果、進行をつなぐルールである。似た操作には似た反応を返し、ユーザーが「こうすると、こうなる」と理解できるようにする。次に進む条件や、できない理由もわかるようにする。

### レベルデザインで段階的に理解を広げる

初回は、少ない操作で小さな成功を体験してもらう。慣れたら、必要な選択肢や活用方法を少しずつ示す。すでに理解している人は、説明を繰り返さずに目的へ進めるようにする。

段階を増やすこと自体を目的にしない。早く用事を済ませたい体験では、少ない段階で終えられることが優先される。

### テンションカーブで集中と余韻を作る

テンションカーブは、体験中の期待、集中、達成感、落ち着きの変化である。場面ごとに、どんな気持ちになってほしいかを考える。

流れの一例は、次のとおり。

**取り組めそうと感じる → 行為に集中する → 結果がわかる → 手応えを感じる → 気持ちよく終える**

常に刺激を強くする必要はない。コンセプトに合わせて、盛り上がる場所と落ち着く場所を作る。

### ゲームサイクルで次に使う理由を作る

ゲームサイクルは、価値を得る一連の行為を、再び行いたくなる循環である。

**使うきっかけ → 意味のある行為 → 心地よい反応 → 価値の実感 → 次に使いたくなる理由**

メモアプリなら「思いつく → 一言残す → 保存の手応えを得る → 頭が軽くなる → 次に思いついたときも残したくなる」という循環を考えられる。

飽きさせないために、使い慣れることで増える価値や、必要に応じた新しい使い方を設計する。毎回の操作を増やしたり、意味のない刺激を加えたりする方向にずれていないか確認する。

繰り返し使いたくなる理由と、気持ちよく終えられる区切りを、両方用意する。継続して使うことも、届けたい体験につながっているかを確かめる。

## 実際の利用の流れで確かめる

画面単体だけでなく、アプリを開くきっかけから目的達成、終了までを通して確認する。説明を読んだかに加えて、何を理解し、どう行動し、何を感じたかを見る。

- 初回で、最初に何をすればよいかわかるか。

- 操作の結果と、自分にとっての価値が伝わるか。

- どこで迷い、止まり、説明を必要としたか。

- なくても困らなかった情報や演出は何か。

- 嬉しい反応が、どの行為の手応えとして届いたか。

- 使い慣れた際に、説明や演出が負担にならないか。

- 自分の意思でまた使いたくなる理由があるか。

迷いが起きたら、その場のUIだけでなく、画面の目的、機能の必要性、届けたい体験まで戻って原因を探す。変更後は、同じ利用の流れをもう一度確かめる。

設計の意図は仮説であり、ユーザーにその体験が届いたかは、実際の行動や感想から確認する。

## サブエージェントで担当を分けて設計と承認を進める

マニュアルに沿った確認は、担当を分けたサブエージェントで行う。主担当エージェントがディレクターとして総責任と進行管理を担い、プランナー、アーティスト、プログラマの専門担当を分ける。変更への影響に応じて必要な審査担当を選び、担当と責任範囲を案件の開始時に明示する。作成者の自己チェックと正式な審査は分け、審査には作成者とは別のサブエージェントを使う。

ユーザーの要望をもとに、ディレクターが体験ベースの要求を示す。下流の担当が順に具体化し、できた案を上流に戻してチェックを受ける。ユーザーが明示した制約や優先順位も、各担当へ引き継ぐ。

**ディレクターが最新の設計一式に対して「実装開始OK」を出すまでは、アプリの実装を始めない。**

### 担当と成果物を分ける

| 担当 | 責任 | 用意する成果物 |
| --- | --- | --- |
| ディレクター | 届けたい体験と優先順位を定め、全体が目的に合うかを判断する | 体験要望、制約、達成条件、最終判断 |
| プランナー | 体験を内容、行為、機能、体験の流れへ具体化する | 体験設計案、情報を教える順序、反応の条件、ゲームサイクル |
| アーティスト | 内容と行為を、画面、UI、視覚表現、動き、音へ具体化する | 画面案、表現意図、嬉しい反応、テンションカーブの表現 |
| プログラマ | 構想段階で技術上の制約を確かめ、体験と表現を実現する方法を具体化する | 早期の技術確認、技術設計、状態と失敗時の挙動、変更範囲、検証方法 |

下流の担当は、上位の目的や承認済みの内容を独断で変更しない。実現が難しい場合は、制約の根拠、体験への影響、代替案を示し、上流へ相談する。

### 成果物と参照できる根拠を審査する

各担当は、対象の版を指定した成果物を提出する。プランナーは利用の流れ、仕様、状態と分岐、達成条件を、アーティストは画面案、遷移、状態ごとの表示、操作と反応の対応を、プログラマは実現方法、変更範囲、検証計画と実施結果を用意する。

審査者が同じ資料、画面、コード、操作記録を確認できるよう、参照先と条件を残す。「確認しました」という報告に加えて、判断を裏付ける対象と根拠を提出する。未実施の検証は計画として明記し、実施結果と混ぜない。

### 下流で具体化して上流へ順に確認を戻す

設計を具体化する標準順は、**ディレクター → プランナー → アーティスト → プログラマ**である。プログラマは構想段階から参加し、画面案を固める前に、体験に影響する技術上の制約と不確実性を確認する。新しい機能や大きな変更では一連の設計を行い、既存の設計を保つ変更では、変更区分に応じて必要な担当案を更新する。作成担当は最新の上流設計と修正履歴を受け取る。審査担当は要求、設計意図、成果物、検証事実を受け取り、今回の自己評価や他担当の合否を見る前に独立して判断する。

1. **ディレクターが体験要望を出す。** 誰に、どんな場面で、何を感じたりできたりしてほしいか、最優先の価値と達成条件を示す。

2. **プランナーが体験設計案を作る。** 内容、機能、行動の流れを具体化する。プログラマと、処理時間、保存と通信、端末や権限など、体験を左右する条件を確認し、ディレクターのチェックを受ける。既存資料やコードで確認できた事実、仮定、試作で確かめる項目を分けて残す。

3. **アーティストが画面と表現を設計する。** プランナー、ディレクターの順にチェックを受ける。

4. **プログラマが実装方針を設計する。** 早期の技術確認をもとに、状態、失敗時の挙動、変更範囲、検証方法を具体化する。自分の技術上の確認を済ませ、アーティスト、プランナー、ディレクターの順にチェックを受ける。

5. **ディレクターが設計一式を最終確認する。** 指摘の解消と各担当の整合性を確認し、対象となる版と範囲を明示して「実装開始OK」を出す。

6. **承認された範囲で実装を始める。** 実装後は、動作検証と、必要なアーティスト、プランナー、ディレクターによる確認を行う。人間が触って確かめる対象は、試作や実装を使って別途確認し、AIの設計審査と分けて記録する。

審査は、**独立判断の記録 → 結果の照合と指摘の処理 → 上流への順次承認**に分ける。同じ版を独立に見る段階は並行してよい。独立判定を保存した後に、前段の合否、指摘、修正履歴と照合する。最終承認は順番に行い、必要なアーティスト、プランナー、ディレクターへ、独立判定と照合結果を渡す。省略する担当と理由は記録し、ディレクターの最終承認は省略しない。

アーティストは表現意図、反応、テンポが維持されるかを確認する。プランナーは内容、行動、体験の流れが成立するかを確認する。ディレクターは、その全体が届けたい体験と最優先の価値に合うかを確認する。各担当は自分の専門範囲を判断し、他の担当の判断を代行しない。

### 画面案を固める前に技術上の条件を確かめる

例えば保存後の反応を設計する場合は、保存にかかる時間、完了と判断する条件、オフラインや失敗時の挙動を先に確認する。プランナーとアーティストは、その条件を操作の流れや反応へ反映する。実現が難しい場合は、プログラマが根拠と代替案を示し、ディレクターが守る体験と変更する範囲を判断する。

調査だけで確かめられない条件は、検証する仮説と必要な試作範囲を示す。実装を伴う試作は、その範囲の実装開始OKを得て進める。早期の技術確認は設計の材料とし、設計一式の審査と実動作の検証は、それぞれの段階で行う。

### 独立判断を先に記録してから結果を照合する

独立審査には、作成者とは別のサブエージェントを使う。新しい審査用の文脈へ、元の要望、承認済みの上流設計、設計意図、同じ版の成果物、制約、検証事実を渡す。作者の自己評価と今回の他担当の合否は、独立判定を記録するまで渡さない。必要な設計意図や、判明している不具合の事実は隠さない。

独立判定を保存した後に、他の審査、前段の指摘、修正履歴と照合する。不一致があれば、争点となる基準と根拠を比べ、追加確認、修正、再審査を行う。他担当の合格や多数決だけで、自分の未解決の指摘を取り下げない。

案が変わった場合は、新しい版として影響範囲を再審査する。独立判定を上書きせず、照合後に判断を変えた理由と、参照した審査IDを追記する。審査の独立性は、役職名だけでなく、別の審査者と入力情報の分け方によって保つ。

### 職種別の合格基準を定める

職種は「どの専門性で判断するか」、レイヤーは「どの範囲を、どの深さで確認するか」である。両方を指定してレビューする。

| 職種 | 専門的に確認する基準 | 確認する資料や根拠 |
| --- | --- | --- |
| ディレクター | 届けたい体験、最優先の価値、制約が守られ、全体の判断に矛盾がないか | 体験要望、各担当の設計、他機能への影響、レビュー結果 |
| プランナー | 内容と機能が必要な行為につながり、理解する順序、反応の条件、繰り返す理由が成立するか | 利用の流れ、機能仕様、状態と分岐、体験の達成条件 |
| アーティスト | 情報の優先順位、画面、視覚表現、動き、音が理解と感情を支え、操作と反応の意味が揃うか | 画面案、表現意図、反応のタイミング、初回と反復時の流れ |
| プログラマ | 要求を実現でき、状態、データ、失敗時の挙動が正しく、他機能への影響と検証方法が明確か | 技術設計、状態遷移、変更範囲、性能や利用条件、検証結果 |

合格には、基準を満たすと判断できる具体的な根拠が必要である。設計段階では目的と設計の対応、実現方法、検証計画を確認する。実装後は実動作の結果も確認する。設計上の合格を、実動作やユーザーの体験が確認できたという判断に転用しない。

### レイヤー別に確認範囲と深さを分ける

選定された全審査担当が、上位の目的と周辺への影響を見る。そのうえで、自分の専門性を使って対象範囲を深く確認する。全体の確認をディレクターだけに任せず、細部の根拠も必要な上流担当へ渡す。

| レイヤー | 確認範囲と深さ | 合格基準 |
| --- | --- | --- |
| L1 コンセプト | 対象ユーザーと体験全体を広く見る。個々の見た目より目的と優先順位を確認する | この案が、届けたい体験と最優先の価値を支えている |
| L2 アプリ全体と他機能 | 他機能、導線、共通ルール、データとの関係を横断して見る | 重複や矛盾がなく、他機能の理解や利用、アプリ全体の体験を損なわない |
| L3 同一機能の整合性 | 対象機能を絞り、仕様、複数画面、UI、状態、分岐を深く見る | 通常、空状態、処理中、成功、失敗、再試行で、仕様と操作と反応がつながる |
| L4 操作や表現や実装の細部 | 特定の要素をさらに絞り、意味、配置、反応、処理を詳しく確かめる | ボタン、文言、動き、タイミング、データ処理などが、承認済みの仕様と意図に合う |

**広く浅く見る**確認では、全体と代表的な利用場面を横断し、方向違いや関係の矛盾を探す。細部をすべて調べる確認とは分けるが、目的との照合を省略しない。

**狭く深く見る**確認では、機能、画面、操作、状態を指定し、その範囲の分岐や例外、繰り返し利用まで追う。単一画面だけを見て、その機能全体を確認した扱いにしない。

どちらの場合も、確認した対象、深さ、未確認の範囲を記録する。代表場面だけの確認を、すべての画面や状態の合格に広げない。専門外の判断が必要なら、該当担当に確認を戻す。

### 担当ごとに重点のレイヤーを決める

全担当に広い視野を持たせたうえで、詳しく確認する範囲を分ける。次を標準配分とし、案件の開始時に各担当へ重点レイヤー、確認範囲、深さを指定する。

| 担当 | 重点レイヤー | 確認の深さと役割 |
| --- | --- | --- |
| ディレクター | L1とL2 | 体験の目的、優先順位、全体の構成を横断して判断する。細部は専門担当の根拠と結論を確認する |
| プランナー | L2とL3 | 他機能との関係を広く見て、対象機能の行動、仕様、情報の順序、分岐を深く確認する |
| アーティスト | L3とL4 | 全体の表現ルールも見ながら、対象機能の画面、状態、表現、反応、反復時のテンポを深く確認する |
| プログラマ | L3とL4 | 他機能や共通データへの影響も見ながら、対象機能の状態、処理、例外、実現方法を深く確認する |

重点の配分は、職種を特定のレイヤーに閉じ込めるためのものではない。選定された全審査担当がL1とL2を確認してから専門範囲を掘り下げ、他のレイヤーも担当の根拠や設計との関係を確認する。周辺への影響が大きい変更では、L2の確認範囲を広げるなど、配分を調整して記録する。

全員に同じ細部を同じ深さで確認させず、専門担当の確認結果を上流が引き継ぐ。ただし、結果を受け取るだけで合格にせず、自分の職種の基準から上位の目的や周辺との整合を確かめる。

### 変更への影響に応じて審査を絞る

変更区分は、差分の行数や作業時間ではなく、体験、意味、行動、機能間の関係への影響で決める。ディレクターが影響の根拠を確認し、必要な職種とレイヤーを選定する。作者の自己申告だけで軽微としない。

| 区分 | 判定の目安 | 審査の範囲 |
| --- | --- | --- |
| 軽微 | 承認済みの意味、行為、流れ、状態、他機能との関係を変えない細部の修正 | 関係する職種が変更箇所を深く確認し、目的と周辺への影響も確認する |
| 通常 | コンセプトと全体構成を保ち、既存機能内の仕様やUIを変える | 影響する職種と必要な上流担当を選び、L1とL2の確認に加えて対象のL3とL4を深く確認する |
| 大きな変更 | 新機能、コンセプト、主要導線、ゲームサイクル、共通ルールやデータ、他機能との関係を変える | 三職種とディレクターで全体を再確認し、変更が及ぶ機能を深く確認する |

文言、色、余白、反応の長さ、音量、反復時のテンポの変更でも、理解、操作、嬉しさに影響するなら軽微にしない。意味が同じでも、心地よさを変える変更は体験への影響で区分する。影響が不明なら審査を省略せず、範囲を広げて確認する。

どの区分でも、元の目的と周辺への影響、成果物と根拠、合否の記録、ディレクターの最終承認は省略しない。省略する担当と項目は、影響がない根拠を示して記録する。省略を合格扱いせず、今回の合格が有効な範囲を明示する。

### 軽微な変更を短く記録する

軽微な変更は、一つの記録に設計審査、承認、実装後の確認を順に追記する。共通のコンセプトや基準は保存版を参照し、変更箇所、判断の根拠、各段階の担当と日時を短く残す。関係する職種の審査は作成者とは別のサブエージェントが行い、独立判定の保存後にディレクターが確認して実装開始OKを記録する。元の判定と承認の履歴は残す。

次は、保存完了メッセージの誤字を直す場合の記入例である。実施結果や承認を示すものではなく、判定欄は実際の確認後に記入する。

| 項目 | 記入例 |
| --- | --- |
| 対象と目的 | 保存完了メッセージ。設計の保存版と差分を参照し、保存できたことを伝える意味を保つ |
| 差分と区分 | 「保存しましした」を「保存しました」へ修正。意味、表示条件、行動、レイアウト、読み上げへの影響を確認して軽微と判断する |
| 必要な担当 | アーティストの独立審査とディレクターの最終承認。プランナーとプログラマの審査を省略する場合は、仕様、処理、他画面への影響がない根拠を参照する |
| 設計審査 | 審査ID、日時、作成者とは別の担当を記入。L1の目的、L2の周辺影響、L3の表示条件、L4の文言を確認し、各判定と根拠を短く残す |
| 承認 | 独立判定の照合後に、ディレクターが承認ID、日時、承認した設計版と実装範囲を追記する |
| 実装後の確認 | 実装版、担当、日時、表示と読み上げの確認結果、未解決の指摘、人間の体験確認の要否と根拠を追記する。必要な確認が済むまで未確認として残す |

意味、操作、心地よさなどへの影響が判明した場合は、変更区分と必要な審査を見直す。軽微な変更でも、根拠不足を合格にしない。

### 広い確認から深い確認へ進める

各審査ではL1とL2で目的と周辺への影響を確認し、選定したL3とL4の範囲を深く確認する。審査者へ、体験要望、全体の機能構成、対象機能の仕様と画面、変更点、検証事実を渡す。独立判断の後に、今回の他担当の合否と指摘を照合する。再審査では修正対象と解消条件を先に渡すが、今回の判定は自分で確かめて記録する。

L1やL2に問題があれば、先に上位の設計を見直す。目的に合わない案を、細部の磨き込みだけで合格にしない。上位を変更した場合は、影響する下位の設計と周辺機能を再確認する。

例えば「思いついたことを迷わず残す」メモアプリなら、次の観点を分ける。

- **L1**：記録の前に細かな分類を必須にして、体験の目的からずれていないか。

- **L2**：記録、検索、整理の導線がつながり、互いの利用を妨げていないか。

- **L3**：入力、保存中、保存完了、失敗、再試行で、仕様とUIが一貫しているか。

- **L4**：保存が完了してから完了表示を出すなど、具体的な処理と反応が合っているか。

各職種は自分の専門基準でこの四つを見る。例えば、アーティストは保存中と完了の見分けや反応のタイミングを、プログラマは対応する状態と処理の正確さを深く確認する。

### レビュー結果と差戻しを記録する

独立判断、照合後の判断、上流の承認を、それぞれの段階でレビュー台帳へ記録する。独立判定を記録するまで、今回の他担当の合否を渡さない。合格にも、何をどの基準でどこまで確認したかを残す。「問題なし」だけでは審査記録にしない。

- **対象**：審査ID、日時、職種と担当、設計審査・実動作審査・人間による体験確認の区別、独立判断・照合・承認の段階、対象の版と参照、変更区分、範囲、レイヤー、確認の深さを記録する。

- **判定**：レイヤーごとと審査全体に、合格、不合格による差戻し、保留のいずれかを付ける。根拠不足や未確認は保留とし、対象外は理由とともに合否とは別に記録する。

- **フィードバック**：対象箇所、適用した基準、期待する状態、確認できた事実や資料、期待との差、体験への影響を記録する。合格の場合も、基準を満たす理由を記録する。

- **修正内容**：指摘ごとに固定の指摘IDを付け、必須修正か改善提案か、担当、直す内容、解消を判断する条件、差戻し先を記録する。

- **再確認**：元の審査IDと指摘IDに、修正回答、修正版、再審査者、確認した根拠、再審査の合否を追記する。修正担当の「対応済み」だけでは解消扱いにしない。

修正が必要なら、担当へ差し戻す。修正で影響する設計を更新し、影響を受ける担当から上流へ順に再レビューを受ける。コンセプトや体験要望が変わった場合は、下流の設計全体を再確認する。

元の指摘や不合格判定を上書きせず、差戻しから解消までの履歴を残す。必須修正を含むレイヤーが一つでも不合格なら、その審査は不合格とする。必要な確認が保留なら、審査全体を合格にしない。返答がないことや、保留をOKと解釈しない。承認済みの内容を変更した場合は、その変更に関係する承認を取り直す。

### 審査と指摘の記録形式

一回のレビューに一つの審査IDを付け、複数のレイヤーを確認した場合は、それぞれの判定と根拠を分ける。対象は版番号やコミットだけでなく、後から同じ内容を確認できる保存版や保管した写しを参照する。更新されるPageや画面案には保存履歴の版、保管した写しの参照、必要に応じて内容ハッシュを併記し、現在のリンクだけで承認対象を示さない。通常と大きな変更では以下の書式を使い、軽微な変更では前述の短い記録に各審査IDと判定をまとめてよい。共通資料や同じ根拠は参照先を記し、全文の転記を繰り返さない。

```text
審査IDと日時：
職種と担当、作成者との区別：
審査種別：設計、実動作、人間による体験確認
段階：独立判断、結果照合、上流承認
対象の版と成果物と根拠の参照：
変更区分、その理由、必要な担当とレイヤー：
対象範囲と確認の深さ：
レイヤーごとの基準、根拠、フィードバック、合否：
省略、対象外、未確認の範囲と理由：
審査全体の合否と、合格が有効な範囲：
照合した審査ID、不一致、処理結果：
指摘一覧と差戻し先：
次に渡す担当：
```

```text
指摘IDと元の審査ID：
対象箇所、職種、レイヤー：
基準、期待する状態、確認した事実、体験への影響：
必須修正 または 改善提案：
修正担当、修正内容、解消条件：
修正回答と修正版：
影響する機能とレイヤー：
再審査ID、担当、根拠、合否：
指摘の状態：未対応、修正中、再審査待ち、解消
```

改善提案は必須修正と区別し、採用するか、その理由も記録する。新しい問題は別の指摘IDで追加し、以前の指摘に混ぜない。指摘を解消とするのは、再審査で解消条件を満たしたと確認したときである。

マニュアル改訂の合否とフィードバックは、改訂の記録に保存する。各アプリの設計でも、案件ごとのレビュー台帳を用意して同じ形式で記録する。

### 設計承認と動作確認と体験確認を区別する

**設計OK**は、対象の設計が目的と専門基準に合うという判断である。**実装開始OK**は、ディレクターが最新の設計と対象範囲の実装を承認した状態である。**動作確認**は、実装したものが仕様どおり動くことの確認であり、**体験確認**は、意図した理解、嬉しさ、テンポなどを実際の利用から確かめることである。**完了**は、その案件で必要と定めた検証と体験確認を終えた状態であり、未確認の体験を含めて完了にしない。

実装開始OKまでは、コードを変更しない調査、設計資料、画面案の作成を進める。アプリへのコード、設定、素材の反映と、実装を伴う試作は実装開始に含める。事前試作にも、影響に応じた審査と、その範囲のディレクターの実装開始OKが必要である。試作の承認を、本実装の承認に転用しない。

最終確認では、体験要望、選定した担当の設計、成果物と根拠、独立判定と照合結果、上流の審査記録、指摘と再審査の履歴を一式で確認する。必要な審査が合格し、必須修正が解消され、省略の理由と未確認事項、対象範囲が明確であることを確認して、ディレクターが実装開始OKを記録する。実装後の確認を設計段階で確認済みにせず、試作や実装で確かめる計画を残す。

### 小さな試作で体験の仮説を確かめる

設計段階で残る仮説は、ディレクターが範囲を承認した小さな試作で確かめる。例えば「保存の反応で安心できる」「説明を読まなくても次の行動がわかる」といった体験の仮説を、実際の画面と操作で確認する。

試作の前に、確かめる仮説、対象範囲、担当、実行条件、観察方法、判定条件、終了条件を決める。その範囲に必要な審査を受けてから、試作の実装開始OKを得る。未確認の仮説があることを記録し、検証するための試作の承認と、本実装の承認を分ける。

AIが確認した動作、ユーザーが取った行動、人間が述べた理解や感想を区別して記録する。理解、嬉しさ、また使いたい気持ちについて、AIの推測を人間の評価として記録しない。誰が、どの版を、どの条件で使い、何を観察したかを残す。

初回の体験、主要な操作、嬉しい反応、継続の理由など、コンセプトに直結する体験を、人間が触って確認する対象として先に決める。必要な人間評価が得られていない項目は未確認として残し、体験を確認済みとしない。試作結果で設計を変更する場合は、影響範囲を再審査してから本実装の実装開始OKを得る。

### 変更の分類から試作までの記入例

既存のメモ機能で、初回説明の順序と保存後の反応を見直す例を考える。コンセプトは「思いついたことを迷わず残し、覚えておく負担を手放す」とする。

変更区分は、体験の目的と全体構成を保ち、機能内の流れと反応を変えるため **通常** とする。プランナーは「まず一言を書く、保存を理解する、分類は必要時に教える」という順序を定める。この段階でプログラマと保存完了の条件、処理時間、オフラインや失敗時の挙動を確認する。アーティストはその条件を踏まえて保存完了の短い反応を設計し、プログラマは保存中、完了、失敗の状態と反応を対応させる。三職種が関係するため、この例では三職種を審査に選ぶ。

試作で確かめる仮説は「補足説明なしで書き始め、保存を理解し、負担が軽くなったと感じられる」である。対象は初回入力から保存までに限定する。動作の判定条件は、保存が完了した場合だけ完了反応を出すこと。体験の観察では、人間がどこで迷ったか、保存をどう理解したか、どう感じたかを記録する。

「次の思いつきも残したい」という感想は、次に使う理由の手がかりとして扱い、実際に再利用した結果とは分ける。事前に決めた操作と観察を終えたら試作を終了し、未確認事項と改善点を整理する。審査、範囲を限定したディレクターの試作承認、試作、動作確認と人間による体験確認、本実装に向けた再審査の順で進める。

## 実案件で運用を確かめて見直す

このマニュアルの運用は、次の一つの機能改善に適用して確かめる。開始時にディレクターが対象範囲と、人間が最初に触って確かめる場面を決める。試作で確かめる不確実性を明示し、その試作に必要な設計と審査を行う。

既存のレビュー記録と試作記録を使い、次の四点を振り返る。

- 審査で実装前に発見できた問題と、その指摘を受けて変えた設計。

- 同じ対象、基準、根拠を繰り返し確認した箇所と回数。専門性によって確認内容が異なるものは区別する。

- 体験要望が決まってから、人間が最初に試作を操作するまでの時間。調査、設計、審査、実装、修正の作業時間と、確認待ちの時間を分けて記録する。

- 人間が触って初めて判明した問題と、その観察から必要になった設計変更。

一件の試作と確認を終えた時点で、ディレクターが各担当の根拠を見て、役に立った審査、統合できる重複、早める確認を決める。担当と確認範囲、記録書式を見直し、変更理由を残す。指摘数や速度だけで効果を判断せず、見逃した問題とユーザーの体験も確認する。必要な人間評価が得られていなければ運用評価は暫定とし、一件の結果だけで他の案件にも有効だと確定しない。

## 変更ごとのレビュー項目

変更の影響に応じて必要な担当とレイヤーを選び、以下の項目を確認する。設計、実動作、人間による体験確認を区別し、該当しない項目と未確認の項目は理由を残す。チェック欄を埋めるために未確認を合格としない。構想段階の技術確認と、軽微な変更の短い記録も、該当する項目の根拠として参照する。

- [ ] 届けたい体験とのつながりを、一文で説明できる。

- [ ] 直上の目的と、コンセプトの両方に合っている。

- [ ] 今理解することと、次にすることが明確である。

- [ ] 後で伝えられる情報や、不要な選択肢を減らしている。

- [ ] アイコン、図形、色、動きに説明できる意図がある。

- [ ] 実際の利用の流れで確かめ、気づきを設計に戻している。

- [ ] 必要な職種を選び、作成担当と審査担当を分け、審査の省略理由を記録している。

- [ ] 独立判定、結果の照合、上流への順次承認を行い、合否と差戻しを記録している。
