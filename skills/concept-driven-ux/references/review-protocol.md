# 担当と独立審査

## 担当と成果物

| 担当 | 成果物と判断の観点 | 重点 |
| --- | --- | --- |
| ディレクター | 体験要望、既存機能の評価範囲、改善対象と案の選定理由、暫定順位と見直す条件、制約、達成条件、全体の価値・配分と最終判断 | L1・L2 |
| プランナー | 既存仕様・機能の役割、内容、行為、結果と負担の評価、維持・変更・統合・削減の比較、機能間の配分、情報の優先順位、状態と分岐、反応条件、再利用の理由 | L2・L3 |
| アーティスト | 画面構成と見つけ方、各状態の表示、表現意図、動きや音、同じレイヤーの強弱・注意競合、テンションカーブ、初回と反復時のテンポ | L3・L4 |
| プログラマ | 早期の技術確認、状態とデータ、失敗と再試行、変更範囲、演出中の情報・操作・時間経過、性能や利用条件、検証計画と結果 | L3・L4 |

全担当がL1・L2を確認してから専門範囲を深く見る。対象と深さを指定し、別担当の専門判断を代行しない。専門的な判断が必要なら担当へ戻す。

| レイヤー | 確認すること |
| --- | --- |
| L1 コンセプト | 既存仕様と案が届けたい体験と最優先の価値を支えるか。維持や改良を選ぶ根拠があるか |
| L2 全体と周辺 | 機能の役割・優先順位・重複は適切か。統合・削減等の影響を含め、導線、共通ルール、データと周辺の利用がつながるか |
| L3 同一機能 | 既存の内容・行為・結果と負担が利用目的に適切か。代案と比べ、通常、空状態、処理中、成功、失敗、再試行の仕様・画面・操作がつながるか |
| L4 細部 | 文言、配置、動き、タイミング、処理が承認済みの意図と仕様に合うか |

広い確認では全体と代表場面を横断する。深い確認では対象の分岐、例外、反復利用を追う。確認していない範囲を合格に含めない。

上位との対応に加え、選んだ各レイヤー内で同じ抽象度の要素を横断比較する。L2なら機能同士の役割・配分、L3なら同一機能の状態・場面同士、L4なら情報・反応・動き同士の関係を見る。広い改善や構成・強弱・タイミングに関わる審査は [全体のバランスとテンションカーブ](experience-balance.md)を使う。全レイヤーの全要素を毎回棚卸ししない。

## 作成担当を動かす

案件で必要な職種を選び、実際のサブエージェントに具体的な成果物を依頼する。能力や同時実行数に合わせて順次進め、役割の数だけ無条件に並列実行しない。既存の設計や有効な承認は、その版・目的・範囲で参照する。広い改善の調査では、過去の承認を現在の妥当性の証明や再検討禁止にしない。

委譲時は次を渡す。

- 元の要望と現在の対象範囲、ユーザーの制約。
- コンセプトと最優先の価値、承認済みの上流設計と保存版。
- 対象の仕様、画面、コードなどの参照先。
- 体験改善では、調査範囲と未確認、既存機能の役割・内容・行為・結果と負担の評価、維持・変更・統合・削減の比較、対象と案の選定理由、残す良さ、観察方法。ユーザーの制約と、再検討できる過去の設計を区別する。
- その担当が作る成果物、担当範囲、重点レイヤー、必要な深さ。
- 確認済みの技術条件、不具合の事実、残る仮説。
- 許可された操作。設計段階はアプリのコード、設定、素材を変更しない。

プランナーとプログラマの早期相談を先に進め、その条件をアーティストへ渡す。下流が上位を変える必要がある場合は、根拠、体験への影響、代替案をディレクターへ返す。

## 新しい文脈で独立審査する

作成者とは別の審査者を使う。サブエージェント起動時に履歴の継承を選べる場合は継承しない。利用できるAPIなら `fork_turns: "none"` を選び、必要な資料だけを渡す。ユーザーの制約は省かない。

審査者へ渡す内容：

- 元の要望、承認済みの上流設計、設計意図、制約。
- 同じ版の成果物、参照できる根拠、検証事実と既知の不具合。
- 体験改善では、現状の機能構成と評価の根拠、比較案、選定理由、改善仮説、残す良さ、比較条件。対象選定と既存仕様の維持も審査できる資料を渡し、選定への賛同を求めない。
- 全体のバランスの審査では、同じレイヤーの比較対象と代表的な並び・同時表示、必須情報と判断、強さ・長さ・頻度の根拠、初回と反復の条件。単体の完成見本だけを渡さず、未確認の周辺や感情効果も示す。
- 審査種別、職種、L1からL4の確認範囲と深さ。
- 合格条件と記録形式。独立判定を返すまで他の合否を参照しないこと。

初回の独立判断まで渡さない内容：

- 作者の「問題ない」「合格だと思う」などの自己評価。
- 今回の他担当の合否と、その合否に基づいた結論。

設計意図や判明した不具合は隠さない。成果物と審査結果が同じファイルにあれば、必要な原資料だけを取り出して渡す。審査者には書き換え権限を必要以上に与えず、指摘と判定を返してもらう。

体験改善の審査者は、現状の機能が何のために必要か、内容・行為・結果は適切か、機能間の重複や優先順位はどうかを、コンセプトと根拠から評価する。次に維持・変更・統合・削減の比較と対象選定を吟味し、改善の見込み、最も大きな弱点・不確実性、失う良さ、利用の負担、確認条件を返す。コードの不備や既存仕様への適合だけで審査を終えない。四種類の案を強制せず、有効な代案を見落とした場合は指摘する。価値が弱ければ対象選定や仕様・内容・行為・構成へ戻し、根拠が足りなければ必要な試作や観察を示す。未検証の効果を確定しない。

関係する要素を通したときの価値・情報・強弱を別に判定する。個別要素が良くても、重要な情報を隠す、次の判断を妨げる、日常の反応と山場の役割を区別できない等の具体的な問題を、単体の魅力で相殺しない。指摘には要素間の関係、該当場面、根拠と目的への影響、差戻し先、成立する代案と解消条件を付ける。「全体のバランスが悪い」だけでは必須修正にしない。感情・疲労・慣れ等の効果が未確認なら検証する仮説として返し、既知の情報・操作の阻害と分ける。

案の選定と詳細設計は、同じ資料で判断できる場合に一回へまとめる。再審査は変更と周辺影響に必要な職種・レイヤーへ絞り、影響しない有効な判定は版・根拠・有効範囲を参照して引き継ぐ。審査の反復を、画面・操作・人間の確認の代わりにしない。

## 判定を記録して照合する

1. 審査者ごとの独立判定を、担当・対象版・基準・根拠・有効範囲とともに保存する。
2. 保存後に他担当の結果、前段の指摘、修正履歴を照合する。不一致は争点と根拠を比べ、追加確認または修正する。
3. 合格・不合格・保留を区別し、対象外には理由を残す。必須修正が残れば不合格、必要な根拠がなければ保留にする。
4. 指摘に固定ID、必須修正か改善提案か、担当、解消条件を付ける。修正版を作ったら影響する範囲を再審査し、「対応済み」という自己申告だけで解消しない。全体のバランスの指摘は関係する系列・同時表示で再確認し、修正した単体だけで解消しない。
5. 独立判定を保持し、照合後に判断を変えた場合は理由と参照した審査IDを追記する。

**試作自身の成立条件と、その試作で確かめる未知を分ける。** 本採用の判断に必要な技術・操作・構成・人間への効果を、許可された限定試作で測る場合、その未知が未確認という理由だけで試作を止めない。試作自身の安全、データ・権限・契約の保護、範囲と実行条件を審査し、検証する未知、観察方法、判定・終了条件を指定した実装開始OKで進める。本採用の合否と感情効果は未確認のまま残す。試作自身に必要な成立条件の根拠が不明、またはその試作範囲に適用する既知の必須修正が未解決なら開始しない。既知の情報・操作の阻害を免除する根拠にしない。

合格の数や多数決だけで未解決の指摘を取り下げない。改善提案は採否と理由を残し、必須修正と分ける。

## 上流へ順に承認を戻す

- プランナー案：ディレクターが確認する。
- アーティスト案：プランナー、ディレクターの順に確認する。
- プログラマ案：アーティスト、プランナー、ディレクターの順に確認する。
- 変更の影響がない担当は根拠を示して省略できる。ディレクターの最終確認は行う。

独立判定は同じ版に対して並行してよい。上流承認では、保存した独立判定、照合結果、解消した指摘と残る項目を受け取る。自分の専門範囲から整合を確かめる。

ディレクターは最新の設計一式、必要な審査、解消済みの必須修正、省略理由、未確認事項と検証計画を確認し、対象版と範囲を指定して実装開始OKを記録する。試作の承認では仮説、範囲、担当、実行条件、観察方法、判定条件、終了条件も確認する。

主担当が案を作った場合、作成者とは別の専門審査で独立性を確保する。主担当の最終承認を「別のディレクターによる独立審査」と記録しない。実際に行っていない担当や審査を記録上で作らない。
